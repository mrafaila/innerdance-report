Chapter 1

Working well in notebooks — before you start

A notebook is easy to start and easy to turn into a mess — cells run out of order, nothing is named clearly, and six months later nobody (including the person who wrote it) can tell what it did or trust the numbers in it. None of that is required. A few habits, followed from the first notebook you write, keep your work something a colleague can open, trust, rerun, and build on.

One notebook, one question

Pick the question before you open a blank notebook — "did RMSSD recover after this session?", not "let's see what's in the data." If a second, unrelated question comes up while you're working, start a new notebook for it rather than growing one notebook into a pile of unrelated explorations. A reader (including you, later) should be able to tell what a notebook is for from its name and its first cell, before reading anything else.

Keep the same shape every time

Every notebook already in this project follows the same order, and yours should too — it's the single biggest thing that makes a notebook skimmable by someone who didn't write it:

  1. Setup — imports, credentials, which session/participant you're looking at.
  2. Load — pull the data you need, print how much you got, so an error shows up here, early, not three steps later as a confusing chart.
  3. Compute — turn raw data into the numbers you actually want.
  4. Plot — look at it.
  5. Interpret — a short written note on what the chart/numbers show, right next to them, while the context is still in your head.

Use a markdown heading (## Load the data, ## Plot RMSSD by stage) for every section. A notebook with no headings asks every future reader to run the whole thing top to bottom just to find the one chart they wanted.

Reuse, don't retype

If a piece of logic already exists — loading a session, computing RMSSD, pulling stage timestamps — import and call it, don't copy it into your own cell. Two copies of the same logic will drift apart the first time either one gets fixed, and then nobody knows which copy is right.

Example
don't Paste the RMSSD formula into a new cell
do from processing.hrv_core import rmssd — then call rmssd(your_rr_values)

When your own code is worth keeping, move it out of the notebook

The first time you write a small function in a notebook, that's fine — it's exploration. The moment you find yourself copying that same function into a second notebook, that's the signal: move it into a shared .py file (processing/ for a metric or data-loading step, analysis/ for a report-building step) instead. From then on every notebook imports the one shared version, a fix or improvement benefits everyone at once, and the core solution grows instead of accumulating parallel, slightly-different copies of the same idea scattered across notebooks. This is what "export as Python to extend the core solution" means in practice — it's a normal, expected step, not a separate advanced skill.

Make it reproducible before you share it

  • Restart, then run all, before sharing. In Colab: Runtime → Restart session and run all. If it only works because of something you ran earlier and then changed, it isn't reproducible yet — a colleague opening it fresh will hit the same break you no longer see.
  • Name outputs so the question is obvious from the filename — a chart saved as figure_1.png tells the next person nothing; rmssd_prepost_rebecca_oct.png does.
  • Comment on the why, not the what. The code already says what it does; a comment earns its place by explaining a reason a reader couldn't otherwise guess — e.g. why a specific threshold, why a stage is excluded.

In one line: write every notebook as if a colleague with no memory of writing it will open it next month, need to understand what it shows within thirty seconds, and be able to rerun it from a clean copy without you in the room.

Chapter 2

Using Google Colab

Google Colab is a free, browser-based way to open and run a notebook — no installation, nothing on your own computer. This chapter is the mechanics: opening a notebook, getting your own access set up, and running it. Chapter 3 then walks through what one specific notebook actually does.

1 Open the notebook link and make your own copy

A shared Colab link opens as read-only — you can look, but not run or edit it. Go to File → Save a copy in Drive. A new tab opens with your own private copy; work in that copy from here on. Nothing you do there affects the shared original, so there's no way to break it for anyone else.

📷 Screenshot needed

The notebook's File menu open, with "Save a copy in Drive" highlighted.

2 Sign in with your Google account

Colab will ask you to sign in if you aren't already. Use the Google account you'd normally use for this project's shared Drive.

3 Set up your access key (once per copy)

You'll have been sent a block of text starting with GITHUB_TOKEN= or similar — this is your personal key to the study database, and is specific to you. In your copy of the notebook:

  1. Click the 🔑 key icon in the left sidebar (Secrets).
  2. Click + Add new secret. Name it exactly ENV_BLOB.
  3. Paste the whole block you were sent into the value field.
  4. Switch on Notebook access for that secret.
📷 Screenshot needed

The left-sidebar Secrets panel, showing the 🔑 icon, the + Add new secret button, and the Notebook access toggle switched on for ENV_BLOB.

Treat that block of text like a password — it's what lets the notebook read study data on your behalf. Don't paste it anywhere except this one Secrets field.

4 Run the notebook

Runtime → Run all runs every cell from the top, in order. The first time, a "Grant access" prompt will appear asking whether the notebook can read your ENV_BLOB secret — click through it; this is what lets the Setup cell work.

📷 Screenshot needed

The Runtime menu with "Run all" highlighted, and separately the "Grant access" permission prompt.

5 Running one cell at a time

Hover over a cell and click the ▶ play button that appears on its left edge, or click into the cell and press Shift + Enter. The next cell becomes active, so pressing Shift + Enter repeatedly steps through the whole notebook one cell at a time — useful for reading each part's output before moving to the next.

📷 Screenshot needed

A single code cell with its ▶ play button visible, and the small running / done indicator that appears to its left.

6 Reading what a cell produces

Output appears directly below the cell that made it: printed numbers/text, a table, or an interactive chart. Charts in these notebooks are usually interactive — hover over a point for its exact value, click-drag to zoom, double-click to reset.

7 If something goes wrong

An error shows as a red box under the cell, with a message at the bottom — that last line is usually the most informative part. Most often:

  • A cell further down was run before an earlier cell finished — fix: Runtime → Restart session and run all, so everything runs in order from a clean state.
  • The ENV_BLOB secret is missing, misnamed, or its Notebook access toggle is off — recheck step 3.

If it's still unclear, copy the exact red error text when asking for help — it's the fastest way for someone else to tell you what's wrong.

📷 Screenshot needed

An example red error box under a cell, showing where the error message text sits.

8 Your work is saved automatically

Colab saves your copy to your Google Drive as you go — there's no separate "save" step. Because it's your copy, your edits and any mistakes stay in your copy only.

Chapter 3

Walkthrough — "Getting started with the session data"

This notebook is the starting point for querying the study database yourself. It already explains each step as you go, with a markdown note above every piece of code — read through it in order first; this section is a short map of what each part is for, not a replacement for reading it.

One thing worth knowing going in: participants appear only as a random id, not a name. The data is pseudonymised, not anonymous — don't export it elsewhere, and don't try to work out who a specific id belongs to.

0. Setup & 1. Connect

Installs what the notebook needs, reads your ENV_BLOB secret (chapter 2, step 3), and opens a connection to the study database using your own personal login. Running this successfully — it prints your username — is what everything else in the notebook depends on.

2. What's in the data

Before querying anything specific, this section just counts rows in each of six tables and previews the sessions table, so you know what exists before you go looking for something in it:

TableOne row per
participantsparticipant (cohort, language, month joined)
sessionssession, with start/rest/end times and artifact %
summary_metricsone pre/post rest window, or one playlist stage, of a session
sliding_metricsa short rolling-window slice through a session
baselinesa participant's own resting reference values

3. Pre vs post resting RMSSD

The simplest "did this help" check: one RMSSD value from the rest window before the playlist, one from after, paired per session, with the typical (median) change across every session that has both.

4. Heart rate and DFA α1 per playlist stage

The same idea stretched across all 12 stages instead of just before/after, averaged across everyone who did a given playlist — this is where you'd look for the activation-then-recovery pattern described in the main project documentation. Stages where the participant was breathing unusually slowly are dropped from this specific chart, since DFA α1 isn't a reliable number in that case.

5. One raw recording, aligned to the stages

Zooms into a single real recording: downloads one person's raw heartbeat data and plots the beat-to-beat intervals as a continuous line, with the playlist's stage boundaries and rest windows shaded on top. This is the one section where you see the actual signal a summary number like "RMSSD" was computed from, rather than just the summary itself.

6. Towards coactivation (illustrative sketch)

A first, intentionally rough look at a more specific pattern: heart rate going up at the same time as a calming (parasympathetic) signal also going up — the two moving together instead of trading off. The notebook itself is explicit that this is a sketch, not a finished method, and flags stages where breathing was too slow to trust the calming-signal reading.

Exploring further with Gemini

Colab has a built-in AI assistant (the Gemini button, bottom centre of the notebook) you can ask in plain language — e.g. "explain what section 4 computes" or "plot mean heart rate per stage for each cohort." The notebook's own closing note is worth repeating here: don't paste raw rows, participant ids, or recordings into it — ask it about the code and the approach, not about specific people's data.

Chapter 4

Walkthrough — three more notebooks

These three go deeper into specific questions than the starting-point notebook in Chapter 3. Each is already commented in detail inline — read through the notebook itself for the mechanics; this section is a short map of what each one is for and why it exists.

1. neurokit_standalone_report.ipynb

notebooks/analysis/neurokit_standalone_report.ipynb

A self-contained version of this project's own session report, deliberately written to use only the public neurokit2 library — no import from this project's own code at all. It exists so the method behind a report (which windows, which metrics, which plots) can be read and checked independently of this project's specific implementation. It can run two ways, switched by one setting near the top: against a local sample file (no database needed — good for first trying it out), or against a real session pulled from the database.

2. stagewise_hrv_tutorial.ipynb

notebooks/analysis/stagewise_hrv_tutorial.ipynb

A full worked example of the question "does the same playlist produce the same stage-by-stage HRV pattern in two different sessions?" — end to end, from a raw database pull through artifact cleaning, computing per-stage metrics for two sessions on the same playlist, plotting both sessions' stage profiles on the same chart, and a correlation check for whether the shapes actually match rather than just looking similar by eye. It's the closest thing in this project to a worked template for "pick two sessions and compare them" — useful to copy as a starting point for a similar comparison of your own.

3. artifact_detection_methods_comparison.ipynb

notebooks/analysis/artifact_detection_methods_comparison.ipynb

A side-by-side check of two different ways to flag a bad heartbeat reading in a raw recording: this project's own method (simple range check, then a rolling comparison against each beat's neighbours), versus a more established method from the Kubios HRV software (via neurokit2). Both are run on the same real recording and the flagged beats are marked on one shared chart, so you can see exactly where the two methods agree or disagree — and the notebook is explicit that on a very clean recording, as most of this project's sessions are, there may be very little for them to disagree on.

All three live in notebooks/analysis/ in the project's own repository — ask your technical contact for access if you'd like to open one directly rather than from the descriptions above.
